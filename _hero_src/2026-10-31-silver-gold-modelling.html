Silver & Gold Modelling: Nested or Exploded?

1The decision

Bronze stays raw and 1:1. In silver, keep one nested row per event and split out an entity only when queries filter, join or aggregate at its grain.

1:1 sub-objects←keep as structs A
Child-field filters←explode: arrays can't cluster B
Every entity costs←writes, OPTIMIZE, checkpoints C D
Gold aggregates←MVs, incremental only on right shapes E

3When to explode an entity?

Keep nested when

  • It's 1:1 with the event (header, device, geo)
  • Read only after filtering on header fields
  • Rarely used or exploratory

Explode to a table when

  • Queries filter or join on a child field
  • Many consumers aggregate at child grain
  • Exact keys needed downstream (posexplode)

Narrow entity table when

  • Filters on a few child fields, wide reads rare
  • Child schema volatile: keys + VARIANT
Hard limits: ≤4 clustering keys · no array/map elements as keys · VARIANT not a key · no shredding inside arrays · MVs: no identity columns

4Under the hood: five mechanisms

AStruct leaves are columns

Struct fields can be clustering keys with dot notation. Only arrays need a decision.

BArrays can't drive skipping

Array and map elements can't be clustering keys, so per-file min/max spans everything.

CEach entity is a new table to run

Storage is the smallest part. Explode where reads pay back the ops.

DFan-out: per sink or foreachBatch

Docs recommend one stream per sink; foreachBatch "reduces parallelization".

EMV refresh: incremental or full

Check planning_information in the event log for the technique used.

5In code

CREATE TABLE silver.entity_items
CLUSTER BY (event_date, sku)            -- child filters
TBLPROPERTIES ('delta.enableRowTracking'='true');

-- deterministic child key: (event_id, item_seq)
SELECT e.event_id, e.event_date, item_seq,
       item.sku, item.qty, item.price
FROM STREAM(silver.event) e
LATERAL VIEW posexplode(e.items) t AS item_seq, item;

CREATE MATERIALIZED VIEW gold.daily_sku_sales
  REFRESH POLICY INCREMENTAL STRICT
  SCHEDULE EVERY 1 HOUR
AS SELECT event_date, sku,
  SUM(CAST(qty*price AS DECIMAL(18,2)))
FROM silver.entity_items GROUP BY ALL;

SELECT `Category`, MEASURE(`Revenue per Buyer`)
FROM gold.sales_metrics GROUP BY ALL; -- metric view

7Key takeaways

  • Silver keeps one validated row per event
  • 1:1 structs stay nested: already columnar
  • Explode arrays only for child-grain filters, joins, aggregates
  • Liquid-cluster every table by its own access pattern
  • Set dataSkippingStatsColumns with hundreds of columns
  • Gold: tables for dims, MVs for aggregates, metric views for measures

Common mistakes

  • Exploding all 20 entities "just in case"
  • Deduping in more than one layer
  • FLOAT sums forcing full MV refreshes
  • Reusing txnAppId with a new checkpoint
Rule of thumb: nested 1:1 silver is the record. Explode an array only when queries filter, join or aggregate on its children.
