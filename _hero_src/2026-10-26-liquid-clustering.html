Databricks Liquid Clustering: How It Works & When to Skip It

A data layout that replaces partitioning and ZORDER. Change clustering keys without rewriting data.

Delta Lake · Unity Catalog
Databricks Runtime 15.4 LTS+
Delta Lake 3.1+ (OSS)

1What is liquid clustering?

You name up to 4 clustering keys. Delta keeps rows with similar key values in the same files, so queries that filter on those keys skip the files they don't need.

Flexible keys←layout in the log A E
Multi-column skipping←Hilbert sort + file stats B C
Cheap maintenance←incremental ZCubes D
Fewer write conflicts←row-level concurrency

3When to use what?

Liquid clustering when

  • Creating a new table (Databricks default)
  • Queries filter on several columns
  • Access patterns change over time
  • Many concurrent writers

Partition + ZORDER when

  • Whole-partition drops or overwrites
  • Partitions never change once written
  • Readers prune by folder / old protocol
  • Runtimes pinned below LC support

No layout when

  • Small tables or mostly full scans
Hard limits: max 4 keys · keys need stats · no complex types · can't mix with partitioning or ZORDER

4Under the hood: five mechanisms

ALayout lives in the log

Keys are a table property in the Delta log (Clustering + DomainMetadata features).

BHilbert, not Z-order

A file is a run of the curve. Fewer jumps → tighter key ranges in every file.

CMin/max stats skip files

No new index: clustering makes the existing per-file stats selective.

DZCubes: incremental OPTIMIZE

Only untagged files are rewritten. OPTIMIZE FULL reclusters everything.

EKey change = metadata commit

Queries stay correct throughout; only skipping improves.

5In code

CREATE TABLE sales.orders (...)
CLUSTER BY (order_date, customer_id);

OPTIMIZE sales.orders;                 -- incremental
ALTER TABLE sales.orders
  CLUSTER BY (region, customer_id);   -- no rewrite
OPTIMIZE sales.orders FULL;            -- recluster old files
ALTER TABLE sales.orders CLUSTER BY AUTO; -- UC managed
DESCRIBE DETAIL sales.orders;          -- shows keys

# streaming: cluster on write
spark.conf.set("spark.databricks.delta.liquid
  .eagerClustering.streaming.enabled", "true")

6What it costs to run

On write
Writer does the extra sort once a transaction passes the size threshold.
Scheduled OPTIMIZE
Your compute clusters small writes later. Every 1–2 h for busy tables.
Predictive optimization
Databricks runs it on billed serverless. Required for CLUSTER BY AUTO.
Falling behind costs speed, not correctness.
ZORDER needs OPTIMIZE too, and re-sorts all it targets.

7Key takeaways

  • Layout lives in the log, so keys change without rewrites
  • Hilbert sort → tight per-file min/max → files skipped
  • ZCubes make OPTIMIZE incremental
  • Run OPTIMIZE FULL after changing keys
  • Protocol upgrade is one-way: check every reader first
  • Keep partitioning when the workload is built around it

Common mistakes

  • Changing keys, never running OPTIMIZE FULL
  • Streaming without the eager-clustering config
  • Enabling LC before checking external readers
Rule of thumb: liquid clustering for new tables. Partition + ZORDER only when the workload is built around the partition column.
Verify: compare files read vs. pruned for your top queries, before and after.
