Is my Spark app over-provisioned?

Two ratios Spark already records: how busy the cores were, and how much memory was touched.

1The two ratios

Slot utilisation: share of the core time you held that ran tasks. Heap headroom: share of the heap you asked for that was ever used.

Slot utilisation←totalDuration ÷ (uptime × totalCores)
Heap headroom←JVMHeapMemory ÷ spark.executor.memory
Driver gaps←wall time not covered by any stage

3What to cut

Cut executors when

  • Utilisation low and heap peak low
  • Few driver gaps on the timeline

Cut memory per executor when

  • Cores busy, heap peak low
  • No spill, GC not shaded red

Fewer cores, same memory when

  • Cores idle, heap peak high

Don't resize when

  • Idle time is driver gaps or one slow task
  • Streaming latency or spot headroom needs it
Thresholds are starting points (e.g. under ~40% busy, under ~50% heap). Tune on your own jobs.

4How each number is built

ASlots held vs slots used

totalDuration sums tasks, so 4 parallel 10 s tasks count as 40 s. Divide by uptime × cores.

BThree shapes of idle

Only the first is a sizing problem. Check the Event Timeline first.

CExecutor memory layout

Each region has its own peak metric. Overhead defaults to 10% of executor memory, with a minimum.

DPick the right denominator

Heap peak ÷ spark.executor.memory. Execution peak ÷ maxMemory.

5In code

# APP = .../api/v1/applications/<id>
ex = [e for e in get("/allexecutors")
      if e["id"] != "driver"]
for e in ex:
    gone = e.get("removeTime") or app_end
    slot_ms += uptime(e, gone) * e["totalCores"]
    busy_ms += e["totalDuration"]

util = busy_ms / slot_ms
heap = to_bytes(props["spark.executor.memory"])
peak = max(e["peakMemoryMetrics"]["JVMHeapMemory"]
           for e in ex) / heap

6Before you trust the numbers

Peaks are sampled
Updated per heartbeat. Set metrics.pollingInterval for faster polling.
Python is invisible by default
processTreeMetrics.enabled=true for PySpark.
Stages get dropped
UI keeps retainedStages (1000). Use the History Server.
Dynamic allocation: use each executor's own uptime.
Cached data pins executors by default.

7Key takeaways

  • Over-provisioning = low busy slots + low heap peak
  • Read both from /allexecutors + /environment
  • Split idle time: driver gaps aren't a sizing problem
  • Divide heap peak by executor memory, not maxMemory
  • Change one dimension at a time

Common mistakes

  • /executors: misses removed executors
  • App duration as executor uptime
  • Cutting executors when one task is skewed
Rule of thumb: cut one step at a time on the same input. Stop when wall time, spill or GC moves.
Verify: utilisation rises; wall time and spill stay flat; no Exec Loss Reason.
